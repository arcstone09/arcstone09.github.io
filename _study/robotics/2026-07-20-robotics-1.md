# CPU & GPU

GPU는 CPU와 별도의 자신만의 메모리 공간(VRAM) 과 명령어 집합(ISA)을 가지고 있다. CPU와 GPU는 PCIe라는 버스로 연결되어 있다.

CPU 프로그램은 어떻게 GPU를 사용하는가? 예를 들어, 아래 c++ 프로그램에서 다음과 같은 CUDA 코드를 작성했다고 하자. 

```c++
int main() {
    ...
    vector_add<<<100,256>>>(a,b,c);
  	...
}
```

컴파일하면 CPU용 코드와, GPU용 코드가 각각 만들어진다. 컴파일된 CPU 프로그램을 수행중, `vector_add<<<100,256>>>(a,b,c);` 부분에서 CPU는 CUDA Runtime에게 "이 함수 실행해. 입력 데이터는 여기 있어." 라고 알려준다.(`call cudaLaunchKernel`) 그러면 CUDA Runtime → GPU Driver → GPU 실행 순으로 전달된다. 

## CUDA

**CUDA**는 NVIDIA가 만든 GPU를 쉽게 사용할 수 있게 해주는 소프트웨어 플랫폼이며, 구성은 아래와 같다.

```scss
CUDA

├── 컴파일러 (nvcc)
├── Runtime
├── Driver API
├── 라이브러리
│     cuBLAS
│     cuDNN
│     cuFFT
└── 개발도구
```

전체 흐름을 보면 아래와 같다.

```scss
C++ 코드 작성
↓
nvcc 컴파일
↓
──────────────────────────
CPU 코드        GPU 코드
──────────────────────────
↓
프로그램 실행
↓
CPU 실행
↓
cudaLaunchKernel()
↓
CUDA Runtime
↓
GPU Driver
↓
PCIe 전송
↓
GPU
↓
GPU 명령어 실행
↓
결과를 VRAM에 저장
↓
필요하면 CPU가 RAM으로 복사
```

1. GPU가 실행할 프로그램을 준비한다. (**CUDA 컴파일러(nvcc)** (컴파일 시) + **CPU 프로그램** (실행 시))

2. GPU가 사용할 데이터와 명령 목록을 메모리에 만든다. (**CUDA Runtime + GPU 드라이버 + CPU**)

3. GPU 드라이버에게 그 작업을 제출한다. (**CPU 프로그램(CUDA Runtime)**)

4. 드라이버가 GPU 하드웨어에 “새 작업이 있다”고 알린다. (**GPU 드라이버**)

5. GPU가 자신의 명령어로 작업을 실행한다. (**GPU**)

```scss
CPU 프로그램
    │
    ├─ GPU 실행 요청 생성
    ├─ CUDA Runtime 호출
    ▼
CUDA Runtime
    │
    ├─ GPU 실행에 필요한 데이터와 명령 목록 생성
    ▼
GPU 드라이버
    │
    ├─ 작업을 GPU 명령 큐에 등록
    ├─ GPU에게 새 작업이 있다고 알림
    ▼
GPU
    │
    └─ 자신의 명령어로 실제 계산 수행
```

## Rendering

화면 렌더링은 다음의 과정을 거친다.

**CPU가 장면을 준비한다.**
물체 위치, 카메라, 조명, 텍스처 등을 정한다.

**CPU가 GPU에 명령을 보낸다.**
“이 모델을 이 셰이더로 그려라” 같은 작업을 명령 버퍼에 넣어 제출한다.

**GPU가 정점을 변환한다.**
3차원 좌표를 모니터의 2차원 좌표로 바꾼다.

**GPU가 삼각형을 픽셀로 바꾼다.**
어떤 화면 픽셀들이 삼각형 내부에 있는지 계산한다. 이를 래스터화라고 한다.

**GPU가 픽셀 색을 계산한다.**
텍스처, 조명, 그림자, 반사 등을 이용해 각 픽셀의 최종 색을 정한다.

**결과를 프레임 버퍼에 저장한다.**
프레임 버퍼는 완성된 한 장의 화면 이미지가 들어 있는 메모리다.

**모니터로 출력한다.**
GPU의 디스플레이 장치가 프레임 버퍼를 읽어 HDMI나 DisplayPort로 모니터에 보낸다.

화면 렌더링이 끝나면 GPU는 완성된 이미지를 **프레임 버퍼(Frame Buffer)**라는 GPU 메모리에 저장한다. 그러면 GPU 안의 **디스플레이 엔진(Display Engine)**이 이 프레임 버퍼를 위에서 아래로 일정한 속도(예: 60Hz면 초당 60번)로 읽어, 픽셀 데이터를 HDMI나 DisplayPort 규격의 디지털 신호로 변환해 모니터로 전송한다. 모니터는 이 신호를 받아 각 픽셀(RGB 서브픽셀)에 필요한 전압이나 전류를 공급하여 LCD는 백라이트를 통과시키는 양을 조절하고, OLED는 픽셀 자체를 발광시켜 최종 화면을 표시한다. 이 과정은 CPU가 픽셀을 하나씩 보내는 것이 아니라, CPU는 "이 프레임 버퍼를 출력해라" 정도만 설정하고 이후에는 GPU의 디스플레이 엔진이라는 전용 하드웨어가 자동으로 반복 수행한다.

**물리적으로는**

GPU 안의 송신 회로가 트랜지스터를 매우 빠르게 ON/OFF 하면서 전선의 전압을 바꾸고(이 과정은 전류 속도에 의존), 이 전압 변화가 케이블을 따라 전자기파 형태로 전달된다(이 과정은 전자기파 속도에 의존). 모니터는 이 전압 변화를 측정하여 다시 0과 1의 비트열을 복원하고, 그 비트열을 RGB 색 값으로 해석해 화면을 표시한다.

# Engine & Simulator

**엔진** 은 **특정 기능을 수행하기 위한 핵심 실행 프로그램**이다. 예를 들어, 게임 엔진의 경우 사용자 입력 → 게임 로직 계산 → 물리 계산 → 충돌 검사 → 애니메이션 → 랜더링 → 화면 출력 과정을 초당 60번 이상 반복한다. 물리 엔진은 공 A와 공 B가 충돌 → 충돌 후 속도 계산, 로봇 관절에 토크 5Nm  → 관절이 얼마나 회전하는지 계산 등의 계산을 하는 프로그램이다. 

**시뮬레이터** 는 현실 세계를 컴퓨터 안에서 최대한 비슷하게 재현하는 프로그램이다. 예를 들어, '공이 떨어진다'는 현실을 구현하기 위해, 시뮬레이터는 중력, 공기저항, 마찰, 질량, 속도를 이용해 실제처럼 떨어지는 모습을 계산한다. 

즉, 시뮬레이터는 목적이고, 엔진은 이를 구현하기 위한 수단이다.

## Mujoco

**MuJoCo**는 **물리 시뮬레이터**이다. 관절 운동, 충돌, 힘 계산, 토크 계산, 접촉 계산에 특화되어 있다.

```xml
<!-- ball.xml -->

<mujoco>
    <worldbody>

        <!-- 바닥 -->
        <geom type="plane" size="5 5 0.1"/>

        <!-- 공 -->
        <body pos="0 0 1">
            <joint type="free"/>
            <geom type="sphere" size="0.05"/>
        </body>

    </worldbody>
</mujoco>
```

MuJoCo 에서는 XML 파일로 세상을 정의한다. 이 XML은 높이 1m에 공 하나, 바닥 하나를 의미한다.

```python
import mujoco
import mujoco.viewer

model = mujoco.MjModel.from_xml_path("ball.xml")
data = mujoco.MjData(model)

with mujoco.viewer.launch_passive(model, data) as viewer:

    while viewer.is_running():

        mujoco.mj_step(model, data)

        viewer.sync()
```

이 코드는 XML파일을 읽어 $\Delta t$ 만큼 물리 계산을 통해 다음 상태를 계산하여 화면에 출력한다.

MuJoCo와 같은 물리 시뮬레이터를 사용하면 직접 물리식을 구현할 필요가 없다. 예를 들어 직접 구현한다면, 아래와 같이 적어야 할 것이다.

```python
velocity += acceleration * dt
position += velocity * dt
```

하지만 MuJoCo에서는 `mujoco.mj_step(model, data)` 한 줄만 호출하면 내부에서 다음과 같은 복잡한 계산을 모두 수행한다.

- 중력 적용, 관성(Inertia) 계산, 관절 운동 방정식, 물체 간 충돌 감지, 접촉력 및 마찰 계산, 제약 조건 해결(관절 제한, 접촉 등), 새로운 위치와 속도 업데이트

## Isaacsim

**Isaac Sim**은 NVIDIA가 만든 **로봇 시뮬레이터**이다. Isaac Sim 안에는 물리 엔진, 렌더링, 카메라, LiDAR, ROS2 연결, 센서, 환경 제작이 모두 들어있다. 

```scss
Isaac Sim
├─ 장면 관리: USD
├─ 물리 계산: NVIDIA PhysX
├─ 화면 렌더링: RTX Renderer
├─ 로봇 제어: Articulation API
├─ 센서 시뮬레이션
├─ Python API
└─ ROS 2 연결 기능
```

예를 들어, 창고 사람, 지게차, 로봇, 카메라, 조명을 모두 만들고 거기서 로봇을 움직일 수 있다. 즉, MuJoCo가 물리 계산 중심이라면 Isaac Sim은 가상 로봇 연구실이다.

아래 코드는 Jetbot의 3D 모델과 물리 정보를 읽어서 (.usd 파일) 가상 세계의 `/World/Jetbot` 위치에 배치하고, 여러 동작을 수행한다.

```python
import carb

import isaacsim.core.experimental.utils.stage as stage_utils
from isaacsim.core.experimental.prims import Articulation
from isaacsim.storage.native import get_assets_root_path


# Isaac Sim 기본 로봇·환경 파일의 위치
assets_root = get_assets_root_path()

if assets_root is None:
    carb.log_error("Isaac Sim asset 경로를 찾을 수 없습니다.")
    raise RuntimeError("Asset root not found")


# 1. 바닥을 Stage에 추가
ground_usd = (
    assets_root
    + "/Isaac/Environments/Grid/default_environment.usd"
)

stage_utils.add_reference_to_stage(
    usd_path=ground_usd,
    path="/World/Ground",
)


# 2. Jetbot 로봇을 Stage에 추가
jetbot_usd = (
    assets_root
    + "/Isaac/Robots/NVIDIA/Jetbot/jetbot.usd"
)

stage_utils.add_reference_to_stage(
    usd_path=jetbot_usd,
    path="/World/Jetbot",
)


# 3. Jetbot을 Python으로 제어할 수 있는 Articulation 객체로 감싼다
jetbot = Articulation("/World/Jetbot")
```



## Unreal Engine

**Unreal Engine** 은 게임을 만드는 엔진이다. 하지만 게임뿐 아니라, 영화, 자율주행, 로봇, 건축에서도 사용된다. 역할은 3D 화면 조명, 그림자, 반사, 재질, 애니메이션의 요소들을 매우 사실적으로 그려주는 것이다. 



## ROS2

**ROS2**는 **로봇 프로그램들을 연결해 주는 미들웨어(framework)**이다.

📝 **MiddleWare**

**Middleware** 란, 중간(middle)에서 여러 프로그램이 서로 대화하도록 도와주는 소프트웨어이다.

로봇이 동작하기 위해, 프로그램이 하나만 실행되는 것이 아니다. 카메라 프로그램, 라이다 프로그램, SLAM 프로그램, 경로계획 프로그램, 모터제어 프로그램 등이 모두 **각각 독립적인 프로그램(Process)** 으로 실행된다. 그러면 camera 프로그램이 planner 프로그램에게 사진을 어떻게 보내지? planner는 controller에게 목적지를 어떻게 전달하지? 와 같은 문제가 생긴다. 이걸 직접 구현하려면 socket, TCP, UDP, shared memory, pipe 등을 모두 직접 구현해야 한다. 

ROS와 같은 미들웨어는 중간에서 모든 프로그램을 연결해준다. 각 프로그램은 미들웨어와 소통하는 코드만 작성하면 된다. 예를 들어, 카메라 노드가 `camera.publish(image);` 라고만 하면 , ROS가 알아서

- 어떤 컴퓨터에 있는지
- 어떤 프로그램이 받을지
- 네트워크를 탈지
- TCP를 사용할지
- 데이터를 직렬화할지

모두 처리한다.

참고로 여기서 `camera.read(image);` 라 적으면 아래와 같이 요청이 내려가 카메라 메모리에 있던 사진 데이터가 프로그램 메모리(image 변수)에 저장되게 된다. 

```scss
camera.read(image)
        │
        ▼
운영체제
        │
        ▼
카메라 드라이버
        │
        ▼
카메라
```

ROS는 그 다음부터 등장한다. 이제 프로그램 메모리 안에 `image`가 있으니까, `publisher.publish(image);` 를 하면 프로그램 메모리(image) → ROS → 다른 프로그램 으로 전달된다. 만약 ROS가 없다면 `socket(), bind(), listen(), accept(), send(), recv()`과 같은 네트워크 코드를 모두 직접 작성해야 한다. 



이제, 로봇의 데이터가 내 컴퓨터로 전송되고 이것이 다시 로봇을 움직이게 하는 전 과정을 알아보자. 로봇과 노트북에서 모두 ROS가 실행된다. 

```scss
┌──────────────────────────┐
│        로봇               │
│                          │
│ Ubuntu + ROS2            │
│                          │
│ 카메라                     │
│ LiDAR                    │
│ 모터                      │
│ IMU                      │
└──────────┬───────────────┘
           │ Wi-Fi
           │
┌──────────▼───────────────┐
│        노트북              │
│                          │
│ Ubuntu + ROS2            │
│                          │
│ SLAM                     │
│ AI                       │
│ 경로계획                   │
└──────────────────────────┘
```

- 로봇 : 카메라가 사진을 찍는다. 
- 로봇 : 운영체제가 카메라 드라이버를 통해 사진을 읽는다.
- 로봇 : 카메라 노드가 영상을 받는다.
  - 예를 들어, camera_node 라는 프로그램이 실행 중이다. `Image img; camera.read(img);`를 수행하면 이제 `img` 변수안에 사진이 들어있다.
- 로봇 : ROS2가 사진을 발행한다. 
  - 카메라 노드는 `publisher.publish(img);` 를 호출한다. 그러면 ROS2의 도움으로 `/camera/image` 토픽으로 사진이 올라간다.
- ROS2가 WIFI로 전송한다. 
  - 노트북에서 `/camera/image` 를 구독하고 있다는 것을 ROS가 알고 있다. 그러면 `로봇 → ROS2 → Wi-Fi → 노트북 →ROS2` 을 통해 데이터를 전송한다.
- 노트북 : 노트북 프로그램이 영상을 받는다.
  - 예를 들어, 노트북에서는 slam_node 라는 프로그램이 실행 중이다. 이 노드는 `subscribe("/camera/image")` 를 하고 있다. 
- 노트북 : slam_node 는 카메라 이미지를 통해 위치를 계산한다. 
- 노트북 : 경로 계획 프로그램 (Planner)이 앞으로 이동할 계획을 계산한다.
- 명령을 다시 ROS2가 WIFI로 전송한다. (`publisher.publish(cmd_vel);`)
- 로봇 : motor_node 프로그램이 데이터를 받는다. 
  - 로봇의 motor_node 프로그램은 `subscribe("/cmd_vel")`을 하고 있다.
- 로봇 : 모터를 움직인다.
  - motor_node는 `motor.setSpeed(left, right);`을 수행한다. 
  - 그러면 motor driver → PWM 신호 → 모터 → 바퀴 회전이 일어난다. 

ROS는 중간에서

- `camera_node` ↔ `slam_node`
- `slam_node` ↔ `planner`
- `planner` ↔ `motor_node`

가 서로 데이터를 주고받도록 연결해 주는 **통신 담당 미들웨어**다.

❓slam_node는 노트북 프로그램이니까 노트북 안에 컴파일 되어있는데 camera_node프로그램 같은 경우는 컴파일된 프로그램을 로봇에 어떻게 이식시키는가?

전제: 로봇 안에 컴퓨터가 들어 있다. 예를 들어 로봇 안에 Jetson이 있다고 하자.

```scss
로봇
└── Jetson
    ├── CPU
    ├── RAM
    ├── SSD
    ├── Ubuntu
    └── ROS2
```

이 Jetson은 화면과 키보드가 없을 뿐 사실상 별도의 컴퓨터다.

노트북과 로봇이 Wi-Fi로 연결되면 보통 SSH로 로봇 컴퓨터에 접속한다.

```scss
ssh robot@192.168.0.20
```

이 명령을 노트북에서 실행하면 터미널은 이제 **로봇 내부 Ubuntu를 원격으로 조작하는 상태**가 된다.

**방법 1. 소스코드를 로봇에 복사하고 로봇에서 컴파일**

① 노트북에서 코드 작성

노트북에 다음 프로젝트가 있다고 하자.

```scss
camera_ws/
└── src/
    └── camera_pkg/
        ├── CMakeLists.txt
        ├── package.xml
        └── src/
            └── camera_node.cpp
```

② 소스코드를 로봇으로 복사

`scp`를 사용할 수 있다.

```scss
scp -r camera_ws robot@192.168.0.20:/home/robot/
```

```scss
노트북 저장장치
camera_ws
    │
    │ Wi-Fi를 통한 파일 전송
    ▼
로봇 저장장치
/home/robot/camera_ws
```

③ SSH로 로봇에 접속

```scss
ssh robot@192.168.0.20
```

④ 로봇에서 컴파일

```scss
cd ~/camera_ws
colcon build
```

`colcon build`가 로봇 내부 CPU에서 C++ 코드를 컴파일한다.

결과적으로 로봇 저장장치에 해당 CPU가 실행할 수 있는 기계어 프로그램이 생긴다.

```scss
camera_node.cpp
      │
      │ 로봇 CPU에서 컴파일
      ▼
camera_node 실행파일
```

⑤ 로봇에서 실행

```scss
source install/setup.bash
ros2 run camera_pkg camera_node
```

그러면 `camera_node`는 로봇 운영체제가 실행하는 프로세스가 된다.

```scss
로봇의 Ubuntu
   │
   └── camera_node 프로세스
         ├── 로봇 카메라 읽기
         └── /camera/image 발행
```

**방법 2. 실행파일을 로봇으로 복사**

노트북에서 먼저 컴파일하고, 만들어진 실행파일을 로봇에 복사할 수도 있다. (CPU 구조가 같아야 한다.)

**방법 3. 크로스 컴파일**

노트북에서 로봇 CPU용 실행파일을 만드는 방법도 있다.



📝 로봇 AI연구에서 Issacsim의 역할

1. 센서 데이터 생성기 (Virtual Sensor)

- Slam_node에서 로봇의 카메라 이미지를 받아 사용하는데, 이런 카메라 이미지를 Isaac Sim과 같은 시뮬레이터로 대신 생성하고 ROS2라는 미들웨어를 이용하여 slam_node 등 다른 프로그램에 전송하는 것이다.
