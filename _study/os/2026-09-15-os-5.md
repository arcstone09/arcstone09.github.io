# The Process

이 장에서는 OS가 사용자에게 제공하는 가장 근본적인 abstraction 중 하나인 **process**에 대해 논의한다. process의 정의는 비공식적으로는 상당히 간단하다. **process란 실행 중인 program이다(running program).** program 자체는 생명력이 없는 존재이다. 그저 disk에 놓여 있는 instructions의 집합(그리고 어쩌면 일부 static data)일 뿐이며, 실행되기를 기다리고 있다. 이 bytes를 가져와 실제로 실행시키고, program을 유용한 무언가로 바꾸는 것이 바로 operating system이다.

우리는 흔히 하나보다 많은 program을 동시에 실행하고 싶어 한다. 예를 들어 desktop이나 laptop을 생각해 보면, web browser, mail program, game, music player 등을 동시에 실행하고 싶을 수 있다. 실제로 일반적인 system에서는 수십 개, 심지어 수백 개의 processes가 동시에 실행되고 있는 것처럼 보일 수 있다. 이렇게 하는 것은 system을 사용하기 편하게 만든다. 사용자는 CPU가 현재 사용 가능한지 걱정할 필요 없이 그냥 program을 실행하면 되기 때문이다.

따라서 우리가 해결해야 할 핵심 문제는 **어떻게 많은 CPU가 존재하는 것 같은 illusion을 제공할 것인가?** 이다. OS는 CPU를 **virtualizing**함으로써 이러한 illusion을 만들어낸다. 하나의 process를 실행한 다음 그것을 멈추고 다른 process를 실행하고, 다시 또 다른 process를 실행하는 식으로 동작함으로써, 실제로는 physical CPU가 하나(또는 몇 개)뿐임에도 불구하고 많은 virtual CPU가 존재하는 것 같은 illusion을 만들어낼 수 있다. 이 기본적인 기법을 CPU의 **time sharing**이라고 부른다.

이를 통해 사용자는 원하는 만큼 많은 concurrent processes를 실행할 수 있다. 다만 그 대가로 performance가 떨어질 수 있다. 여러 process가 CPU를 공유해야 한다면 각각의 process가 더 느리게 실행될 수 있기 때문이다. CPU virtualization을 구현하고, 그것을 잘 구현하기 위해서 OS에는 low-level **machinery**와 high-level **intelligence**가 모두 필요하다. 

- low-level machinery를 **mechanisms**라고 부른다. mechanism은 필요한 functionality를 구현하는 low-level method 또는 protocol이다.

예를 들어 이후에 **context switch**를 구현하는 방법을 배우게 된다. context switch는 OS가 특정 CPU에서 하나의 program 실행을 멈추고 다른 program을 실행할 수 있도록 해준다. 이러한 time-sharing mechanism은 모든 현대 OS에서 사용된다. 

이러한 mechanisms 위에는 OS의 일종의 intelligence가 존재하며, 이것이 **policies**의 형태로 구현된다. policy는 OS 내부에서 어떤 결정을 내리기 위한 algorithm이다. 예를 들어 CPU에서 실행 가능한 여러 program이 있다고 하자. **어떤 program을 OS가 실행해야 하는가?** 이 결정을 OS의 **scheduling policy**가 내린다. 이때 다음과 같은 정보가 사용될 수 있다.

- historical information: 예를 들어 지난 1분 동안 어떤 program이 더 많이 실행되었는가?
- workload knowledge: 어떤 종류의 program들이 실행되고 있는가?
- performance metrics: system이 interactive performance를 최적화하려는가, 아니면 throughput을 최적화하려는가?

📝 **Time/Space sharing**

**time sharing**은 OS가 resource를 공유하기 위해 사용하는 기본적인 기법이다. time sharing과 대응되는 개념은 **space sharing**이다. space sharing에서는 하나의 resource를 공간적으로 나누어 여러 사용자가 사용한다. 예를 들어 disk space는 자연스럽게 space-shared resource이다. 어떤 block이 하나의 file에 할당되면, 일반적으로 사용자가 그 file을 삭제하기 전까지 그 block은 다른 file에 할당되지 않는다.

# 4.1 The Abstraction: A Process

OS가 제공하는 "실행 중인 program"에 대한 abstraction을 우리는 **process**라고 부른다.

앞서 말했듯이 process는 단순히 running program이다.

어떤 순간의 process를 설명하려면, 그 process가 실행되는 동안 접근하거나 영향을 주는 system의 여러 부분을 조사하면 된다.

process가 무엇으로 구성되는지를 이해하기 위해서는 process의 **machine state**를 이해해야 한다.

즉,

> program이 실행 중일 때 무엇을 읽거나 update할 수 있는가?

를 알아야 한다.

특정 시점에서 이 program의 실행에 중요한 machine의 부분들이 무엇인지 생각해 보자.

process를 구성하는 machine state의 명백한 요소 중 하나는 **memory**이다.

instructions는 memory에 존재한다. 실행 중인 program이 읽고 쓰는 data 역시 memory에 존재한다.

따라서 process가 address할 수 있는 memory, 즉 **address space**는 process의 일부이다.

**registers** 역시 process의 machine state에 포함된다.

많은 instruction들이 명시적으로 register를 읽거나 update하기 때문에 register 역시 process 실행에서 매우 중요하다.

특히 중요한 몇몇 register들이 존재한다.

예를 들어 **program counter (PC)** —*때로는 **instruction pointer (IP)**라고도*한다 — 는 program의 어느 instruction이 다음에 실행될지를 알려준다.

마찬가지로 **stack pointer**와 그와 관련된 **frame pointer**는 function parameters, local variables, return addresses를*위한 stack을 관리하는 데 사용된다.

# TIP: SEPARATE POLICY AND MECHANISM

많은 operating system에서 일반적으로 사용되는 design paradigm은 high-level **policy**와 low-level **mechanism**을 분리하는 것이다.

mechanism은 system에 대한 **how** 질문에 답한다고 생각할 수 있다.

예:

> operating system은 **어떻게** context switch를 수행하는가?

반면 policy는 **which** 질문에 답한다.

예:

> operating system은 지금 **어떤** process를 실행해야 하는가?

둘을 분리하면 mechanism 자체를 다시 설계하지 않고도 policy를 쉽게 변경할 수 있다.

따라서 이는 일반적인 software design principle인 **modularity**의 한 형태이다. 

마지막으로 program은 흔히 **persistent storage devices**에도 접근한다.

따라서 process의 I/O 관련 정보에는 현재 process가 열어 둔 file들의 list 등이 포함될 수 있다.

# 4.2 Process API

실제 process API에 대한 논의는 다음 장으로 미루지만, 여기서는 operating system의 interface에 반드시 포함되어야 할 것들이 무엇인지 간략히 살펴보자.

이러한 API들은 어떤 형태로든 모든 현대 operating system에서 제공된다.

- **Create:** operating system에는 새로운 process를 생성할 수 있는 방법이 있어야 한다. shell에 command를 입력하거나 application icon을 double-click하면 OS가 호출되고, 지정한 program을 실행하기 위한 새로운 process를 생성한다.
- **Destroy:** process creation을 위한 interface가 있는 것처럼, system은 process를 강제로 destroy하기 위한 interface도 제공한다. 물론 많은 process는 작업을 완료하면 스스로 exit한다. 하지만 그렇지 않은 경우 사용자는 process를 kill하고 싶을 수 있으므로 runaway process를 중지시킬 수 있는 interface가 유용하다.
- **Wait:** 어떤 경우에는 process의 실행이 끝날 때까지 기다리는 것이 유용하다. 따라서 일종의 waiting interface가 제공되는 경우가 많다.
- **Miscellaneous Control:** process를 kill하거나 기다리는 것 외에도 다른 control이 가능하다. 예를 들어 대부분의 OS는 process를 **suspend**하여 잠시 실행되지 않게 하고, 이후 **resume**하여 다시 실행하게 하는 방법을 제공한다.
- **Status:** process가 얼마나 오랫동안 실행되었는지 또는 현재 어떤 state인지와 같은 status information을 얻기 위한 interface도 일반적으로 존재한다. 

# 4.3 Process Creation: A Little More Detail

이제 program이 어떻게 process로 변환되는지 조금 더 자세히 살펴보자.

구체적으로 OS는 어떻게 program을 실제로 실행 가능한 상태로 만드는가?

process creation은 실제로 어떻게 동작하는가?

OS가 program을 실행하기 위해 가장 먼저 해야 하는 것은 program의 **code**와 **static data**(예: initialized variables)를 memory,*즉 process의 **address space**로 load하는 것이다.

program은 처음에는 disk 또는 일부 현대 system에서는 flash-based SSD에 어떤 executable format으로 저장되어 있다.

따라서 program과 static data를 memory에 load하려면 OS가 disk에서 해당 bytes를 읽어 memory 어딘가에 배치해야 한다.

### Figure 4.1: Loading: From Program To Process

페이지 4의 그림은 이 과정을 보여준다.

Disk에는

```
Program → code + static data
```

가 존재한다.

OS가 이를 읽어 Memory의 process address space로 가져오며, process에는 대략

```
code
static data
heap


stack
```

이 존재한다.

즉 그림에 적힌 **Program Loading**은 다음과 같다.

> disk에 있는 program을 가져와 process의 address space 안으로 읽어 들인다.

초기의 단순한 operating system에서는 loading을 **eagerly**,*즉 program을 실행하기 전에 한꺼번에 전부 수행했다.

현대 OS는 이 작업을 **lazily** 수행한다. 즉 program execution 중 실제로 필요해졌을 때 code나 data의 일부만 load한다.

code와 data의 lazy loading이 실제로 어떻게 가능한지 제대로 이해하려면 이후 memory virtualization에서 다룰 **paging**과 **swapping**에 대해 이해해야 한다.

지금은 program을 실행하기 전에 OS가 disk에서 중요한 program bits를 memory로 가져오기 위한 작업을 해야 한다는 점만 기억하면 된다. 

code와 static data가 memory에 load된 후에도 process를 실행하기 전에 OS가 해야 할 일이 몇 가지 더 있다.

먼저 program의 run-time **stack**을 위한 memory를 allocate해야 한다.

C program은 local variables, function parameters, return addresses를 위해 stack을 사용한다. OS는 이 memory를 allocate하여 process에 제공한다.

또한 OS는 일반적으로 arguments를 사용해 stack을 initialize한다.

구체적으로 `main()` function의 parameters인 `argc`와 `argv` array를 채워 넣는다.

OS는 program의 **heap**을 위한 memory도 allocate할 수 있다.

C program에서 heap은 명시적으로 요청되는 dynamically-allocated data를 위해 사용된다.

program은 `malloc()`을 호출하여 이러한 공간을 요청하고, `free()`를 호출하여 명시적으로 해제한다.

heap은 linked lists, hash tables, trees 등의 data structure를 위해 필요하다.

처음에는 heap이 작다. program이 실행되면서 `malloc()` library API를 통해 더 많은 memory를 요청하면, OS가 개입하여 해당 요청을 만족시키기 위해 process에 추가 memory를 allocate할 수 있다.

OS는 특히 **I/O**와 관련된 여러 initialization 작업도 수행한다.

예를 들어 UNIX system에서는 각 process가 기본적으로 세 개의 열린 **file descriptor**를 가진다.

- standard input
- standard output
- standard error

이 descriptor들을 통해 program은 terminal에서 쉽게 input을 읽고 screen에 output을 출력할 수 있다.

I/O와 file descriptor 등에 대해서는 이 책의 세 번째 부분인 persistence에서 더 자세히 다룬다.

code와 static data를 memory에 load하고, stack을 생성 및 initialize하고, I/O setup과 관련된 기타 작업을 수행하면 OS는 마침내 program execution을 위한 준비를 끝낸다.

이제 마지막 작업이 하나 남았다.

program의 **entry point**,*즉 `main()`에서 실행을 시작하는 것이다.

OS는 `main()` routine으로 jump함으로써 CPU의 control을 새롭게 생성된 process에 넘긴다.

그 결과 program execution이 시작된다. 

# 4.4 Process States

process가 무엇이고 대략 어떻게 생성되는지 알았으니, 이제 특정 시점에 process가 가질 수 있는 여러 **state**를 살펴보자.

단순화해서 보면 process는 다음 세 가지 state 중 하나에 있을 수 있다.

**Running:** process가 processor 위에서 실행되고 있는 state이다. 즉 instructions를 실행하고 있다는 뜻이다.

**Ready:** process가 실행될 준비는 되어 있지만 어떤 이유로 OS가 현재 이 process를 실행하지 않기로 선택한 state이다.

**Blocked:** process가 어떤 operation을 수행했고, 다른 event가 발생하기 전까지는 실행될 준비가 되지 않은 state이다.

대표적인 예가 disk에 I/O request를 보내는 경우다.

process가 disk I/O를 시작하면 blocked 상태가 되고, 그동안 다른 process가 processor를 사용할 수 있다. 

### Figure 4.2: Process: State Transitions

페이지 6의 그림은 다음과 같은 state transition을 보여준다.

```
                 Scheduled
        Ready --------------> Running
          ^                     |
          |                     |
          |    Descheduled      |
          +---------------------+

Running -- initiate I/O --> Blocked
Blocked -- I/O done ------> Ready
```

OS의 판단에 따라 process는 **Ready ↔ Running** 사이에서 이동할 수 있다.

Ready → Running으로 이동하는 것은 process가 **scheduled**되었다는 뜻이다.

Running → Ready로 이동하는 것은 **descheduled**되었다는 뜻이다.

process가 I/O operation을 시작하는 등의 이유로 blocked가 되면, OS는 특정 event가 발생할 때까지 process를 blocked 상태로 유지한다.

예를 들어 I/O가 완료되면 process는 다시 Ready state로 이동한다.

OS가 그렇게 결정한다면 곧바로 Running으로 이동할 수도 있다. 

두 process가 이러한 state 사이를 어떻게 이동하는지 예를 들어 살펴보자.

먼저 두 process 모두 CPU만 사용하고 I/O는 수행하지 않는다고 하자.

### Figure 4.3: Tracing Process State: CPU Only

| Time | Process0 | Process1 | Notes             |
| ---- | -------- | -------- | ----------------- |
| 1    | Running  | Ready    |                   |
| 2    | Running  | Ready    |                   |
| 3    | Running  | Ready    |                   |
| 4    | Running  | Ready    | Process0 now done |
| 5    | –        | Running  |                   |
| 6    | –        | Running  |                   |
| 7    | –        | Running  |                   |
| 8    | –        | Running  | Process1 now done |

즉 Process0가 먼저 CPU를 사용하여 끝까지 실행되고, 그동안 Process1은 Ready 상태에서 기다린다.

Process0가 끝나면 Process1이 Running이 된다.

다음 예에서는 첫 번째 process가 일정 시간 실행된 후 I/O를 요청한다.

그 순간 process는 blocked되고, 다른 process가 실행될 기회를 얻게 된다.

### Figure 4.4: Tracing Process State: CPU and I/O

| Time | Process0 | Process1 | Notes                  |
| ---- | -------- | -------- | ---------------------- |
| 1    | Running  | Ready    |                        |
| 2    | Running  | Ready    |                        |
| 3    | Running  | Ready    | Process0 initiates I/O |
| 4    | Blocked  | Running  | Process0 is blocked    |
| 5    | Blocked  | Running  | so Process1 runs       |
| 6    | Blocked  | Running  |                        |
| 7    | Ready    | Running  | I/O done               |
| 8    | Ready    | Running  | Process1 now done      |
| 9    | Running  | –        |                        |
| 10   | Running  | –        | Process0 now done      |

좀 더 구체적으로 보면 Process0가 I/O를 시작한 뒤 I/O 완료를 기다리면서 blocked된다.

예를 들어 process가 disk에서 무언가를 읽거나 network에서 packet이 도착하기를 기다릴 때 blocked될 수 있다.

OS는 Process0가 CPU를 사용하지 않는다는 것을 알아차리고 Process1을 실행한다.

Process1이 실행되는 동안 I/O가 완료되고 Process0는 다시 Ready로 이동한다.

마지막으로 Process1이 종료되면 Process0가 다시 실행되고 종료된다. 

이 단순한 예에서도 OS가 내려야 하는 결정이 많이 있다는 점에 주목하자.

첫째, Process0가 I/O를 수행하는 동안 system은 Process1을 실행하기로 결정했다.

이렇게 하면 CPU를 계속 busy 상태로 유지할 수 있기 때문에 **resource utilization**이 향상된다.

둘째, Process0의 I/O가 완료되었을 때 system은 즉시 Process0로 다시 switch하지 않기로 결정했다.

이것이 좋은 결정인지는 명확하지 않다.

어떻게 생각하는가?

이러한 종류의 결정은 **OS scheduler**가 내린다. scheduler에 대해서는 이후 장에서 다룬다.

# 4.5 Data Structures

OS도 하나의 program이다.

따라서 다른 program과 마찬가지로 여러 중요한 정보를 추적하기 위한 핵심 **data structures**를 가지고 있다.

예를 들어 각 process의 state를 추적하기 위해 OS는 Ready 상태인 모든 process를 위한 일종의 **process list**와 현재 어떤 process가 Running인지 추적하기 위한 추가 정보를 유지할 것이다.

OS는 blocked processes도 어떤 방식으로든 추적해야 한다.

I/O event가 완료되면 OS는 올바른 process를 깨워 다시 Ready 상태로 만들어야 하기 때문이다.

Figure 4.5는 xv6 kernel에서 OS가 각 process에 대해 어떤 종류의 정보를 추적해야 하는지를 보여준다.

Linux, Mac OS X, Windows와 같은 실제 operating system에도 이와 비슷한 process structure가 존재한다. 물론 훨씬 복잡하다. 

### Figure 4.5: The xv6 Proc Structure

```
// the registers xv6 will save and restore
// to stop and subsequently restart a process
struct context {
    int eip;
    int esp;
    int ebx;
    int ecx;
    int edx;
    int esi;
    int edi;
    int ebp;
};

// the different states a process can be in
enum proc_state {
    UNUSED, EMBRYO, SLEEPING,
    RUNNABLE, RUNNING, ZOMBIE
};

// the information xv6 tracks about each process
// including its register context and state
struct proc {
    char *mem;                  // Start of process memory
    uint sz;                    // Size of process memory
    char *kstack;               // Bottom of kernel stack
                                // for this process
    enum proc_state state;      // Process state
    int pid;                    // Process ID
    struct proc *parent;        // Parent process
    void *chan;                 // If !zero, sleeping on chan
    int killed;                 // If !zero, has been killed
    struct file *ofile[NOFILE]; // Open files
    struct inode *cwd;          // Current directory
    struct context context;     // Switch here to run process
    struct trapframe *tf;       // Trap frame for the
                                // current interrupt
};
```

그림에서 OS가 process에 대해 추적하는 몇 가지 중요한 정보를 볼 수 있다.

**register context**에는 멈춰 있는 process의 register 내용이 저장된다.

process가 중지되면 process의 registers가 이 memory location에 저장된다.

이 registers를 restore, 즉 저장했던 값들을 실제 physical registers에 다시 넣으면 OS는 process 실행을 다시 시작할 수 있다.

이 기법이 바로 이후 장에서 배우게 될 **context switch**이다. 

그림을 보면 process가 Running, Ready, Blocked 외에도 다른 state에 있을 수 있음을 알 수 있다.

예를 들어 system에는 process가 생성되고 있는 동안 존재하는 initial state가 있을 수 있다.

또 process가 exit했지만 아직 정리되지 않은 final state에 놓일 수도 있다.

# ASIDE: DATA STRUCTURE — THE PROCESS LIST

Operating system에는 앞으로 살펴볼 여러 중요한 data structure가 가득하다.

**process list** 또는 **task list**는 그중 첫 번째다.

상대적으로 단순한 data structure이지만, 여러 program을 동시에 실행할 수 있는 OS라면 system에서 실행되는 모든 program을 추적하기 위해 반드시 이와 비슷한 structure를 가지고 있어야 한다.

process 하나에 대한 정보를 저장하는 개별 structure를 **Process Control Block (PCB)**이라고*부르기도 한다.

거창하게 들리지만, 사실 각 process에 대한 정보를 담고 있는 C structure를 가리키는 말이다.

이를 **process descriptor**라고 부르기도 한다. 

UNIX-based system에서 process가 exit했지만 아직 cleanup되지 않은 상태를 **zombie state**라고 한다.

이 final state가 유용한 이유는 다른 process, 보통 해당 process를 생성한 parent process가 종료된 process의 **return code**를 확인할 수 있기 때문이다.

이를 통해 방금 종료된 process가 성공적으로 실행되었는지 확인할 수 있다.

일반적으로 UNIX-based system에서는 program이 task를 성공적으로 수행하면 `0`을 return하고, 그렇지 않으면 non-zero 값을 return한다.

확인이 끝나면 parent는 마지막으로 `wait()` 같은 call을 수행한다.

이는 child가 완료되기를 기다리는 동시에, 이제 OS가 종료된 process를 가리키던 관련 data structures를 cleanup해도 된다는 것을 알려주는 역할을 한다.

> Footnote: 그렇다. 정말 이름이 zombie state다. 실제 zombie와 마찬가지로 이 zombie들도 비교적 쉽게 kill할 수 있다. 다만 일반적으로는 서로 다른 방법을 사용하는 것이 권장된다. 

# 4.6 Summary

우리는 OS의 가장 기본적인 abstraction인 **process**를 소개했다.

process는 매우 간단하게 말하면 **running program**으로 볼 수 있다.

이러한 conceptual view를 바탕으로 이제 더 구체적인 내용으로 넘어갈 것이다.

즉 process를 구현하기 위해 필요한 low-level **mechanisms**와 process들을 지능적으로 schedule하기 위해 필요한 high-level **policies**를 살펴본다.

mechanisms와 policies를 결합함으로써 operating system이 CPU를 어떻게 **virtualize**하는지 이해하게 될 것이다. 

# ASIDE: KEY PROCESS TERMS

**Process**는 running program을 나타내는 주요 OS abstraction이다.

특정 시점의 process는 process의 state를 통해 설명할 수 있다. 여기에는 다음이 포함된다.

- address space 안의 memory contents
- CPU registers의 contents — program counter, stack pointer 등
- I/O 관련 정보 — 예를 들어 읽거나 쓸 수 있도록 열려 있는 files

**Process API**는 program이 process와 관련하여 호출할 수 있는 calls로 구성된다. 일반적으로 creation, destruction 및 기타 유용한 calls가 포함된다.

process는 Running, Ready, Blocked 등 여러 **process states** 중 하나에 존재한다.

scheduled/descheduled되거나 I/O 완료를 기다리는 것과 같은 event가 process를 한 state에서 다른 state로 transition시킨다.

**process list**에는 system의 모든 process에 대한 정보가 들어 있다.

각 entry는 흔히 **Process Control Block (PCB)**이라고*불리는 곳에 존재한다. PCB는 실제로는 특정 process에 대한 정보를 담고 있는 structure이다.

# 5.1 The `fork()` System Call

`fork()` system call은 새로운 process를 생성하는 데 사용된다.

하지만 미리 경고하자면, 이것은 여러분이 평생 호출하게 될 routine 중 가장 이상한 것일 가능성이 높다.

좀 더 구체적으로 살펴보자. 실행 중인 program의 code가 Figure 5.1과 같다고 하자. code를 살펴보거나, 더 좋은 방법으로는 직접 입력해서 실행해 보라.

> **Footnote 1:** 물론 이것이 확실하다고 우리가 정말 알고 있는 것은 아니다. 아무도 보고 있지 않을 때 여러분이 어떤 routine을 호출하는지 누가 알겠는가? 하지만 여러분의 routine-calling pattern이 아무리 특이하더라도 `fork()`는 꽤 이상하다.

## Figure 5.1: Calling `fork()` (`p1.c`)

```
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int main(int argc, char *argv[]) {
    printf("hello (pid:%d)\n", (int) getpid());
    int rc = fork();

    if (rc < 0) {
        // fork failed
        fprintf(stderr, "fork failed\n");
        exit(1);
    } else if (rc == 0) {
        // child (new process)
        printf("child (pid:%d)\n", (int) getpid());
    } else {
        // parent goes down this path (main)
        printf("parent of %d (pid:%d)\n",
               rc, (int) getpid());
    }

    return 0;
}
```

이 program(`p1.c`)을 실행하면 다음과 같은 결과를 볼 수 있다.

```
prompt> ./p1
hello (pid:29146)
parent of 29147 (pid:29146)
child (pid:29147)
prompt>
```

`p1.c`에서 무슨 일이 일어났는지 자세히 이해해 보자.

처음 실행되었을 때 process는 `hello` message를 출력한다. 이 message에는 자신의 **process identifier**,*즉 **PID**가 포함되어 있다.

이 process의 PID는 `29146`이다.

UNIX system에서는 process에 무언가를 하고 싶을 때, 예를 들어 실행을 중지시키고 싶을 때 PID를 이용해 해당 process를 지정한다.

여기까지는 특별할 것이 없다.

이제 흥미로운 부분이 시작된다.

process가 `fork()` system call을 호출한다.

`fork()`는 새로운 process를 생성하기 위해 OS가 제공하는 방법이다.

이상한 점은 **새롭게 생성된 process가 `fork()`를 호출한 process의 거의 정확한 copy라는 것**이다.

따라서 OS 입장에서는 이제 `p1`이라는 program의 두 copy가 실행되고 있는 것처럼 보이며, 둘 모두 `fork()` system call에서 return하려는 상태가 된다.

새롭게 생성된 process를 **child**,*이를 생성한 기존 process를 **parent**라고 한다.

여기서 child는 예상할 수 있는 것처럼 `main()`에서 실행을 시작하지 않는다.

실제로 `"hello"` message가 한 번만 출력되었다는 점을 주목하라.

대신 child는 **마치 자기 자신이 `fork()`를 호출했던 것처럼** 그 지점에서 생겨난다. 

------

## 그런데 child는 완전히 동일한 copy는 아니다

다음 Figure 5.2의 code를 보자.

# Figure 5.2: Calling `fork()` And `wait()` (`p2.c`)

```
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

int main(int argc, char *argv[]) {
    printf("hello (pid:%d)\n", (int) getpid());
    int rc = fork();

    if (rc < 0) { // fork failed; exit
        fprintf(stderr, "fork failed\n");
        exit(1);
    } else if (rc == 0) { // child (new process)
        printf("child (pid:%d)\n", (int) getpid());
    } else { // parent goes down this path
        int rc_wait = wait(NULL);
        printf("parent of %d (rc_wait:%d) (pid:%d)\n",
               rc, rc_wait, (int) getpid());
    }

    return 0;
}
```

child가 parent의 **완전히 동일한 copy는 아니라는 점**을 눈치챘을 수도 있다.

child는 이제 자신의

- address space, 즉 private memory
- registers
- PC

등을 가지고 있다.

하지만 `fork()`가 caller에게 return하는 값이 parent와 child에서 서로 다르다.

구체적으로,

**parent**

```
fork() → 새로 생성된 child의 PID
```

를 받는다.

반면 **child**

```
fork() → 0
```

을 받는다.

이러한 차이는 매우 유용하다.

덕분에 위 code처럼 parent와 child의 두 경우를 서로 다르게 처리하는 code를 간단하게 작성할 수 있다. 

또 한 가지 중요한 사실이 있다.

`p1.c`의 output은 **deterministic하지 않다.**

child process가 생성되고 나면 우리가 관심 있는 active process가 두 개 존재한다.

- parent
- child

단순화를 위해 single CPU system에서 실행한다고 하자.

그러면 이 시점에서 child가 먼저 실행될 수도 있고 parent가 먼저 실행될 수도 있다.

앞의 example에서는 parent가 먼저 실행되어 message를 먼저 출력했다.

하지만 다음과 같이 반대 결과가 나올 수도 있다.

```
prompt> ./p1
hello (pid:29146)
child (pid:29147)
parent of 29147 (pid:29146)
prompt>
```

특정 순간에 어떤 process가 실행될지는 **CPU scheduler**가 결정한다.

scheduler는 상당히 복잡하기 때문에 일반적으로 어떤 process를 먼저 선택할지에 대해 강한 assumption을 할 수 없다.

따라서 어떤 process가 먼저 실행될지도 보통 확정할 수 없다.

이러한 **non-determinism**은 특히 multi-threaded program에서 흥미로운 문제들을 발생시킨다.

책의 두 번째 부분에서 **concurrency**를 공부할 때 이러한 non-determinism을 훨씬 더 많이 보게 될 것이다. 

# 5.2 The `wait()` System Call

지금까지는 별로 대단한 일을 하지 않았다.

message 하나를 출력하고 exit하는 child를 생성했을 뿐이다.

하지만 parent가 child process가 하던 일을 끝낼 때까지 기다리는 것이 유용한 경우가 많다.

이 작업을 수행하는 것이 `wait()` system call이다.

또는 더 완전한 형태인 `waitpid()`를 사용할 수도 있다.

Figure 5.2의 `p2.c`에서는 parent process가 `wait()`를 호출한다.

그러면 child가 실행을 끝낼 때까지 parent는 **block**,*즉 execution이 지연된다.

child가 끝나면 parent가 **unblocked**되고 parent의 `wait()`가 return한다.

앞의 code에 `wait()` call을 추가하면 output이 **deterministic**해진다.

왜 그런지 알겠는가?

한번 생각해 보라.

*(생각하기를 기다리는 중... 이제 됐다.)*

조금 생각해 보았으니 output을 살펴보자.

```
prompt> ./p2
hello (pid:29266)
child (pid:29267)
parent of 29267 (rc_wait:29267) (pid:29266)
prompt>
```

이 code에서는 이제 **child가 항상 먼저 출력한다**는 것을 알 수 있다.

왜 그런가?

child가 처음부터 먼저 실행되었다면 당연히 parent보다 먼저 출력한다.

반대로 parent가 먼저 실행되었다고 하자.

parent는 곧바로 `wait()`를 호출한다.

이 system call은 child가 실행되어 exit할 때까지 return하지 않는다.

따라서 parent가 먼저 실행되었더라도 parent는 child가 실행을 끝낼 때까지 얌전히 기다린다.

child가 종료되고 나서야 `wait()`가 return하고, 그다음 parent가 자신의 message를 출력한다. 

> **Footnote 2:** child가 exit하기 전에 `wait()`가 return하는 몇 가지 경우가 존재한다. 언제나 그렇듯 자세한 내용은 man page를 읽어라. 또한 이 책에서 "child가 항상 먼저 출력된다" 또는 "UNIX는 세상에서 가장 좋은 것이며 심지어 ice cream보다도 좋다" 같은 절대적이고 조건 없는 주장을 할 때는 조심해서 받아들여라.

# 5.3 Finally, The `exec()` System Call

process creation API의 마지막으로 중요한 요소가 `exec()` system call이다.

`exec()`는 **현재 calling program과 다른 program을 실행하고 싶을 때** 유용하다.

예를 들어 `p2.c`에서 `fork()`만 사용하면 같은 program의 copy를 계속 실행하는 데에만 유용하다.

하지만 실제로는 다른 program을 실행하고 싶은 경우가 많다.

바로 그것을 `exec()`가 해준다.

> **Footnote 3:** Linux에는 `exec()`의 여섯 가지 variant가 있다: `execl()`, `execlp()`, `execle()`, `execv()`, `execvp()`, `execvpe()`. 자세한 내용은 man page를 읽어라.

# Figure 5.3: Calling `fork()`, `wait()`, And `exec()` (`p3.c`)

```
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <string.h>
#include <sys/wait.h>

int main(int argc, char *argv[]) {
    printf("hello (pid:%d)\n", (int) getpid());
    int rc = fork();

    if (rc < 0) { // fork failed; exit
        fprintf(stderr, "fork failed\n");
        exit(1);
    } else if (rc == 0) { // child (new process)
        printf("child (pid:%d)\n", (int) getpid());

        char *myargs[3];
        myargs[0] = strdup("wc");    // program: "wc"
        myargs[1] = strdup("p3.c");  // arg: input file
        myargs[2] = NULL;            // mark end of array

        execvp(myargs[0], myargs);   // runs word count
        printf("this shouldn’t print out");
    } else { // parent goes down this path
        int rc_wait = wait(NULL);
        printf("parent of %d (rc_wait:%d) (pid:%d)\n",
               rc, rc_wait, (int) getpid());
    }

    return 0;
}
```

이 example에서 child process는 `wc` program을 실행하기 위해 `execvp()`를 호출한다.

`wc`는 word-counting program이다.

여기서는 source file인 `p3.c`를 대상으로 `wc`를 실행한다.

따라서 file에 존재하는 line, word, byte의 수를 알려준다.

```
prompt> ./p3
hello (pid:29383)
child (pid:29384)
29 107 1030 p3.c
parent of 29384 (rc_wait:29384) (pid:29383)
prompt>
```

`fork()` system call도 이상하지만 그 파트너인 `exec()`도 평범하지 않다.

`exec()`가 하는 일을 살펴보자.

executable의 이름(예: `wc`)과 arguments(예: `p3.c`)가 주어지면 해당 executable의 **code와 static data를 load**하고 현재 process의 code segment와 static data를 그것으로 **overwrite**한다.

program의 memory space에 있는 heap, stack 등의 다른 부분도 다시 initialize된다.

그다음 OS는 해당 program을 실행하며 arguments를 그 process의 `argv`로 전달한다.

따라서 중요한 점은:

> **`exec()`는 새로운 process를 생성하지 않는다.**

대신 현재 실행 중인 program(원래 `p3`)을 **다른 running program(`wc`)으로 변환한다.**

child에서 `exec()`가 실행된 후에는 거의 `p3.c`가 실행된 적이 없었던 것처럼 된다.

그리고 **성공한 `exec()` call은 return하지 않는다.**

# TIP: GETTING IT RIGHT (LAMPSON’S LAW)

Lampson은 유명한 논문 *Hints for Computer Systems Design*에서 다음과 같이 말한다.

> "제대로 만들어라. abstraction도 simplicity도 제대로 만드는 것을 대신할 수 없다."

때로는 그냥 올바른 일을 해야 한다.

그리고 그렇게 제대로 해냈을 때는 다른 alternative들보다 훨씬 낫다.

process creation을 위한 API를 설계하는 방법은 많이 있다.

그러나 `fork()`와 `exec()`의 combination은 단순하면서도 엄청나게 강력하다.

여기서 UNIX designer들은 그냥 **제대로 만들었다.**

그리고 Lampson이 워낙 자주 "제대로 만들었기" 때문에 이 법칙을 그의 이름을 따서 부른다. 

# 5.4 Why? Motivating The API

여기서 큰 의문이 하나 생길 수 있다.

새 process를 생성한다는 단순해 보이는 작업을 위해 왜 이렇게 이상한 interface를 만들었을까?

그 이유는 `fork()`와 `exec()`를 **분리한 것**이 UNIX shell을 만드는 데 핵심적이기 때문이다.

둘이 분리되어 있기 때문에 shell은

```
fork()
   ↓
[여기서 원하는 작업 수행]
   ↓
exec()
```

처럼 `fork()`를 호출한 뒤 `exec()`를 호출하기 **전에** code를 실행할 수 있다.

이 code를 이용해 곧 실행될 program의 **environment를 변경할 수 있다.**

그리고 이것이 여러 흥미로운 feature를 쉽게 구현할 수 있도록 해준다.

**shell 자체도 그냥 user program이다.**

shell은 prompt를 보여주고 사용자가 무언가를 입력할 때까지 기다린다.

사용자가 command, 즉 executable program의 이름과 arguments를 입력한다.

대부분의 경우 shell은 다음 과정을 수행한다.

1. file system에서 executable이 어디에 존재하는지 찾는다.
2. `fork()`를 호출하여 command를 실행할 새로운 child process를 생성한다.
3. `exec()`의 variant 중 하나를 호출하여 command를 실행한다.
4. `wait()`를 호출하여 command가 완료될 때까지 기다린다.
5. child가 완료되면 `wait()`에서 return한다.
6. shell은 다시 prompt를 출력하고 다음 command를 기다린다.

> **Footnote 4:** shell에는 여러 종류가 있다. 예를 들어 `tcsh`, `bash`, `zsh` 등이 있다. 하나를 골라 man page를 읽고 더 자세히 배워보라. 모든 UNIX expert가 그렇게 한다. 

`fork()`와 `exec()`를 분리하면 shell이 다양한 유용한 기능을 아주 쉽게 수행할 수 있다.

예를 들어 다음 command를 보자.

```
prompt> wc p3.c > newfile.txt
```

여기서는 `wc` program의 output이 `newfile.txt`라는 output file로 **redirect**된다.

`>` 기호가 이러한 redirection을 나타낸다.

shell이 이를 구현하는 방법은 매우 단순하다.

child가 생성되면 `exec()`를 호출하기 전에 shell, 더 정확히 말하면 child process에서 실행되는 code가

1. standard output을 close하고
2. `newfile.txt`를 open한다.

그러면 곧 실행될 `wc` program의 모든 output이 screen이 아니라 file로 보내진다.

그 이유는 **open file descriptor들이 `exec()` call 이후에도 open 상태로 유지되기 때문**이다.

Figure 5.4는 정확히 이 작업을 수행하는 program이다.

이 redirection이 가능한 이유는 OS가 file descriptor를 관리하는 방법과 관련되어 있다.

UNIX system은 사용 가능한 file descriptor를 찾을 때 **0부터 검색하기 시작한다.**

이 경우 standard output을 close했으므로 `STDOUT_FILENO`가 가장 먼저 사용 가능한 file descriptor가 된다.

따라서 이후 `open()`을 호출하면 새롭게 연 file에 이 번호가 할당된다.

그 결과 child process가 standard output file descriptor에 `write`하는 모든 작업, 예를 들어 `printf()`를 통한 output은 screen이 아니라 새롭게 열린 file로 투명하게 route된다. 

`p4.c`를 실행한 결과는 다음과 같다.

```
prompt> ./p4
prompt> cat p4.output
32 109 846 p4.c
prompt>
```

이 output에서 최소 두 가지 흥미로운 점을 확인할 수 있다.

첫째, `p4`를 실행했을 때 겉보기에는 아무 일도 일어나지 않은 것처럼 보인다.

shell은 그냥 command prompt를 다시 출력하고 곧바로 다음 command를 받을 준비를 한다.

하지만 실제로 아무 일도 일어나지 않은 것은 아니다.

`p4`는 실제로 `fork()`를 호출하여 새로운 child를 생성했고, `execvp()`를 호출하여 `wc` program을 실행했다.

screen에 output이 보이지 않는 이유는 output이 `p4.output` file로 redirect되었기 때문이다.

둘째, `cat`으로 output file을 확인하면 `wc` 실행에서 예상한 output이 모두 들어 있음을 볼 수 있다.

멋지지 않은가?

------

**UNIX pipe**도 비슷한 방식으로 구현되지만 `pipe()` system call을 사용한다.

이 경우 한 process의 output을 **in-kernel pipe**,*즉 queue에 연결하고 다른 process의 input을 같은 pipe에 연결한다.

따라서 한 process의 output이 자연스럽게 다음 process의 input으로 사용된다.

그 결과 길고 유용한 command chain을 연결할 수 있다.

간단한 example로 file에서 특정 word를 찾고 그 word가 몇 번 나타나는지 세고 싶다고 하자.

`grep`, `wc`, pipe를 사용하면 간단하다.

```
grep -o foo file | wc -l
```

command prompt에 이것을 입력하고 결과를 감상해 보라.

지금까지 process API를 high level에서 간단히 살펴봤지만, 이러한 call들에는 훨씬 많은 detail이 있다.

예를 들어 file descriptor에 대해서는 책의 세 번째 부분에서 file system을 다룰 때 더 자세히 배운다.

지금은 **`fork()`/`exec()` combination이 process를 생성하고 manipulate하는 강력한 방법**이라는 것만 알아두면 충분하다. 

# Figure 5.4: All Of The Above With Redirection (`p4.c`)

```
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <string.h>
#include <fcntl.h>
#include <sys/stat.h>
#include <sys/wait.h>

int main(int argc, char *argv[]) {
    int rc = fork();

    if (rc < 0) {
        // fork failed
        fprintf(stderr, "fork failed\n");
        exit(1);
    } else if (rc == 0) {
        // child: redirect standard output to a file
        close(STDOUT_FILENO);
        open("./p4.output", O_CREAT|O_WRONLY|O_TRUNC,
             S_IRWXU);

        // now exec "wc"...
        char *myargs[3];
        myargs[0] = strdup("wc");    // program: wc
        myargs[1] = strdup("p4.c");  // arg: file to count
        myargs[2] = NULL;            // mark end of array

        execvp(myargs[0], myargs);   // runs word count
    } else {
        // parent goes down this path (main)
        int rc_wait = wait(NULL);
    }

    return 0;
}
```

# 5.5 Process Control And Users

`fork()`, `exec()`, `wait()` 외에도 UNIX system에는 process와 상호작용하기 위한 많은 interface가 존재한다.

예를 들어 `kill()` system call은 process에 **signal**을 보내는 데 사용된다.

여기에는 process를 pause하거나 종료시키는 등의 directive가 포함된다.

편의를 위해 대부분의 UNIX shell에서는 특정 key combination이 현재 실행 중인 process에 특정 signal을 보내도록 설정되어 있다.

예를 들어:

```
Ctrl-C → SIGINT
```

`SIGINT`는 interrupt signal을 process에 보내며 일반적으로 process를 terminate시킨다.

```
Ctrl-Z → SIGTSTP
```

`SIGTSTP`는 stop signal을 보내 process 실행을 중간에 pause한다.

이후 많은 shell에서 제공하는 `fg` 같은 built-in command를 이용해 다시 resume할 수 있다. 

전체 **signals subsystem**은 external event를 process에 전달하기 위한 풍부한 infrastructure를 제공한다.

개별 process에서 signal을 receive하고 process하는 방법도 있고, 개별 process뿐 아니라 전체 process group에 signal을 보내는 방법도 있다.

이 communication 방식을 사용하기 위해 process는 `signal()` system call을 사용하여 다양한 signal을 **catch**할 수 있다.

그러면 특정 signal이 process에 전달되었을 때 process는 normal execution을 suspend하고 해당 signal에 대응하는 특정 code를 실행한다.

signal의 여러 복잡한 detail에 대해서는 다른 자료를 참고하라.

그렇다면 자연스럽게 다음 질문이 생긴다.

> 누가 process에 signal을 보낼 수 있고, 누가 보낼 수 없는가?

일반적으로 우리가 사용하는 system에서는 여러 사람이 동시에 system을 사용할 수 있다.

그중 한 사람이 마음대로 다른 process에 `SIGINT` 같은 signal을 보내 process를 interrupt하고 terminate시킬 수 있다면 system의 usability와 security가 크게 손상될 것이다.

따라서 현대 system에는 **user**라는 개념이 강하게 존재한다.

user는 credentials를 증명하기 위해 password를 입력한 후 login하고 system resource에 접근한다.

그다음 하나 또는 여러 process를 launch할 수 있고, 자신이 생성한 process를 pause하거나 kill하는 등 완전한 control을 행사할 수 있다.

일반적으로 user는 **자신의 process만 control할 수 있다.**

OS의 역할은 CPU, memory, disk 등의 resource를 각 user와 그 process에 분배하여 system 전체의 목표를 만족시키는 것이다.

# 5.6 Useful Tools

유용한 command-line tool도 많이 있다.

예를 들어 `ps` command를 사용하면 현재 어떤 process들이 실행되고 있는지 볼 수 있다.

유용한 flag들은 man page에서 확인하라.

`top` 역시 매우 유용하다.

system의 process들과 각 process가 얼마나 많은 CPU 및 기타 resource를 잡아먹고 있는지를 보여준다.

재미있게도 `top`을 실행하면 종종 `top` 자기 자신이 가장 많은 resource를 잡아먹는 process라고 주장한다.

어쩌면 약간 egomaniac인지도 모른다.

`kill` command를 사용하면 process에 임의의 signal을 보낼 수 있다.

조금 더 user-friendly한 `killall`도 같은 용도로 사용할 수 있다.

이것들은 조심해서 사용해야 한다.

실수로 자신의 window manager를 kill하면 눈앞의 computer를 사용하기가 상당히 어려워질 수 있다.

마지막으로 system load를 빠르게 파악할 수 있는 여러 종류의 **CPU meter**가 있다.

저자들은 예를 들어 Macintosh toolbar에서 MenuMeters를 항상 실행하여 현재 CPU가 얼마나 utilization되고 있는지 확인한다고 한다.

일반적으로 현재 system에서 무슨 일이 벌어지고 있는지에 대한 정보는 많을수록 좋다. 

# ASIDE: THE SUPERUSER (ROOT)

system에는 일반 user처럼 제한되지 않고 system을 관리할 수 있는 user가 일반적으로 필요하다.

이 user는 자신이 생성하지 않은 process라 하더라도, 예를 들어 system을 악용하고 있는 process라면 임의로 kill할 수 있어야 한다.

또한 `shutdown`과 같은 강력한 command도 실행할 수 있어야 한다.

`shutdown`은 이름에서 예상할 수 있듯 system을 종료한다.

UNIX-based system에서는 이러한 특별한 권한을 가진 user를 **superuser**,*또는 **root**라고 부른다.

대부분의 일반 user는 다른 user의 process를 kill할 수 없지만 superuser는 할 수 있다.

root가 되는 것은 Spider-Man이 되는 것과 비슷하다.

> **큰 힘에는 큰 책임이 따른다.**

따라서 security를 높이고 큰 실수를 피하기 위해서는 일반적으로 regular user로 사용하는 편이 낫다.

root가 되어야 한다면 매우 조심해야 한다.

computing 세계의 모든 파괴적인 힘이 이제 여러분의 손끝에 있기 때문이다.
